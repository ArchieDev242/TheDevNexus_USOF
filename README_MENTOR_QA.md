# Технічні питання від ментора

## 1. Яка основна мета цього форуму?
**Питання:** Для кого створено TheDevNexus та яку проблему ви вирішуєте?

**Відповідь:** Форум орієнтований на україномовних розробників ігор та модів. Ми прагнемо створити простір, де професіонали та ентузіасти можуть ділитися досвідом, обговорювати рушії (Unreal, Unity, Godot, Ren'Py, GameMaker, CryEngine) і навіть власні розробки на OpenGL/Vulkan, не втрачаючи контексту української спільноти.

## 2. Як реалізовано автентифікацію користувачів?
**Питання:** Який стек використано для логіну та які механізми безпеки застосовані?

**Відповідь:** На бекенді (Node.js + Express) користувачі проходять реєстрацію/логін через JWT. Паролі хешуються за допомогою bcrypt, токени зберігаються в HTTP-only cookies. Middleware перевіряє підпис та строки дії токена, що унеможливлює доступ до захищених маршрутів без валідної сесії.

## 3. Яка структура бази даних?
**Питання:** Як організовано зберігання постів, категорій та взаємодій користувачів?

**Відповідь:** MySQL схема включає таблиці `users`, `posts`, `categories`, `comments`, `likes`, `notifications`, `reports`. `posts` посилається на `users` та `categories`, а також містить поля стану (чернетка/закрито). Індекси на `publish_date` та `category_id` забезпечують швидке фільтрування стрічки.

## 4. Що робить фронтенд при завантаженні сторінки "Forums"?
**Питання:** Як формується список постів та фільтри?

**Відповідь:** React SPA (Webpack) викликає `fetch_posts()` та `fetch_categories()` через Redux-thunks. Потім виконується клієнтська пагінація (10 постів на сторінку) з мемоізацією результатів. Користувач може фільтрувати за категорією або сортувати за датою/популярністю, що тригерить повторний запит та ресет сторінки.

## 5. Як ви гарантуєте безпечний рендер Markdown контенту?
**Питання:** Чи є захист від XSS під час показу постів/коментарів?

**Відповідь:** На фронтенді використовуємо `react-markdown` із `remark-gfm`, а також `rehype-sanitize` та `hast-util-sanitize` з кастомним аловлістом. Це дозволяє залишити базове форматування, але блокує скрипти, iframe та небезпечні атрибути.

## 6. Як працює система сповіщень?
**Питання:** Звідки береться рахунок непрочитаних та як він оновлюється?

**Відповідь:** Після логіну фронтенд кожні 30 секунд робить запит на `/api/notifications/unread/count`. Бекенд повертає кількість відфільтрованих за користувачем непрочитаних записів. Після відкриття дропдауну та відповідних API викликів статуси позначаються як прочитані.

## 7. Як обробляються зображення аватарів?
**Питання:** Чому вони скрізь коректно відображаються та які кроки обробки?

**Відповідь:** Upload виконується через Multer, після чого `sharp` нормалізує розмір і обрізає центр кадру. На фронтенді для будь-яких зображень застосовано `object-fit: cover` та резервний `/user/avatar.jpg`, що гарантує круглу рамку без викривлень.

## 8. Чим відрізняється клієнтська пагінація від серверної?
**Питання:** Чому ви робите зріз вже отриманих постів, а не запитуєте сторінки з бекенду?

**Відповідь:** REST API вже повертає відсортований набір (дефолтно 10 елементів). Клієнтська пагінація використовується як "шар кешу" для миттєвого перемикання без додаткового мережевого запиту, зберігаючи UX на рівні. Для великих масивів можна переключитися на server-driven пагінацію, оскільки код розділено на окремий хук.

## 9. Як побудовано міжнародну підтримку інтерфейсу?
**Питання:** Які мови доступні та як перемикання впливає на стан додатку?

**Відповідь:** i18next, три набора перекладів (`en`, `de`, `ua`). Перемикач збережений у локальному стані через власний хук `useLanguage`. Redux та React-компоненти автоматично перерендерюються при зміні `currentLanguage`, додаткових серверних викликів не потрібно.

## 10. Як організований процес деплойменту?
**Питання:** Які кроки необхідні, аби розгорнути проєкт у продакшені?

**Відповідь:** 1) Розгорнути MySQL та виконати `db.sql`. 2) Налаштувати `.env` (JWT секрети, SMTP). 3) Запустити бекенд (`npm start`) за протоколом HTTPS/PM2. 4) Зібрати фронтенд (`npm run build`) і віддати `frontend/dist` через CDN/Nginx. 5) Забезпечити реверс-проксі для маршрутизації API та SPA.

## 11. Які є потенційні вузькі місця продуктивності?
**Питання:** Де виникатимуть проблеми при зростанні трафіку?

**Відповідь:** Найкритичніші точки – запити з агрегаціями (підрахунок лайків/коментарів), синхронні поштові відправлення в `MailService`, рендер довгих тем із великою кількістю Markdown. Рішення: індексувати відповідні поля, перенести розсилки в чергу (наприклад, BullMQ), додати server-side pagination з кешем Redis.

## 12. Як ви обробляєте репорти та модерацію?
**Питання:** Що відбувається, коли користувач скаржиться на пост?

**Відповідь:** Фронтенд відправляє payload (тип контенту, ID, причина) на `/api/reports`. Бекенд зберігає запис у таблиці `reports`, сповіщає модераторів електронною поштою. Адміни через AdminJS-панель можуть переглянути список, змінити статус (в роботі, закрито), а також закрити пост чи заблокувати автора.

## 13. Як реалізовано захист від CSRF?
**Питання:** Використання cookies підвищує ризик, які запобіжники передбачено?

**Відповідь:** JWT знаходяться в HTTP-only cookies, запити до API потребують `Authorization` заголовок дублювати не потрібно. З фронтенду дія відбувається через `fetch` з `credentials: 'include'`. Для критичних дій можна додати двофакторну перевірку токеном у тілі запиту. На продакшн-сервері слід увімкнути `SameSite=strict` та `Secure` прапорці.

## 14. Як би ви масштабували систему сповіщень?
**Питання:** Який підхід використали б для реального часу?

**Відповідь:** Перехід з polling на WebSocket (socket.io) або SSE. Сервер відправлятиме push-сповіщення при створенні нових коментарів або лайків. Для горизонтального масштабування варто додати брокера повідомлень (Redis pub/sub), щоб синхронізувати події між інстансами.

## 15. Що буде, якщо поштовий сервіс недоступний?
**Питання:** Чи блокуватиме це користувацькі дії?

**Відповідь:** Ні, критичні запити повертають успіх навіть якщо `MailService` кидає виняток (логуються попередження). Для покращення надійності плануємо retry-чергу та fallback SMTP провайдера. Крім того, повідомлення модератору дублюється в таблиці `notifications`.

## 16. Як відбувається робота з мультимовними категоріями?
**Питання:** Якщо назви категорій мають локалізацію, як вона підвантажується?

**Відповідь:** Бекенд повертає `title` та, за наявності, `title_translations` JSON. Клієнт визначає активну мову і відображає відповідне поле. Якщо переклад відсутній, використовується базова назва, що забезпечує graceful degradation.

## 17. Що станеться, якщо користувач спробує виконати SQL-ін'єкцію?
**Питання:** Які заходи безпеки реалізовані в контролерах?

**Відповідь:** Всі запити виконуються через `mysql2` із параметризованими виразами (`?`). Навіть якщо атаку вдасться внести в текст посту, вона буде зберігатися як звичайний рядок, адже система санітує HTML при рендері.

## 18. Як ви тестуєте застосунок?
**Питання:** Чи є автоматизовані тести?

**Відповідь:** Наразі фокус на manual QA: `npm run build --prefix frontend` для пошуку компіляційних помилок, smoke-тести маршрутизації та модерації. У планах – додати unit-тести для сервісів (Jest) і інтеграцію REST (Supertest).

## 19. Які кроки потрібно виконати новому розробнику для старту?
**Питання:** Що б ви порадили члену команди, який щойно приєднався?

**Відповідь:** Пройти README, налаштувати `.env`, підняти MySQL, запустити `npm run dev` для фронтенду та `npm run dev` для бекенду. Переглянути `backend/docs/` для API опису, `frontend/src/i18n/` для перекладів, а також `frontend/src/components/` щоб зрозуміти архітектуру UI.

## 20. Які наступні кроки розвитку?
**Питання:** Що заплановано після поточного релізу?

**Відповідь:** Додати real-time стрічку, покращити SEO через SSR, інтегрувати систему бейджів, міграцію на PostgreSQL з JSONB для зберігання перекладів і впровадити CI/CD pipeline з лінтингом та автоматичними збірками.
